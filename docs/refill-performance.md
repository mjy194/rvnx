# CF 补备调度优化与复测

测试日期：2026-10-31。已去掉成功筛选后强制等待 60 秒的补备冷却，改为提升备用后立即准备下一条，并用独立的下载配额控制测速流量。

同样的 75 秒压力场景中，新建模型请求首段最大延迟从 **14,837.927 ms 降到 28.217 ms**，没有再出现触及 112 次预算后等待备用的长尾。300 次新连接模型请求、300 次 Keep-Alive 请求和 1,500 次真实 SSH 回显全部成功。此前结果保留在 [优化前报告](streaming-performance.md)，原始数据未覆盖。

## 改动

- 备用提升或丢失后立即补备，让当前主连接还拥有充足预算时就开始准备下一条。成功不触发冷却；整轮无合格候选时才等待 `retry_secs`，默认 60 秒。
- 启动仍按原策略建立 6 个候选、各 4 MiB，前两名再各测两次 16 MiB，共 88 MiB。
- 正常补备优先在当前健康主连接的 IP 上建立**新的 TLS 连接**，每次测 8 MiB、两次取最低速度，仍须达到 100 Mbps。首个合格候选即停止；失败才尝试其他候选，每轮最多 2 条。没有继承旧连接的分数。
- 正常补备首个候选合格时只需 16 MiB，相比重做 88 MiB 完整筛选少约 82%。样本比启动复测短，可通过 `refill_download_mib` 提高到 16 MiB，并相应调整配额。
- 启动、补备和健康下载共用本客户端的配额桶：默认补充 64 MiB/分钟，桶容量及初始配额 96 MiB。单次测量仍全速进行。下载前预扣请求大小，失败不退款；零字节保活及协议头开销不计入此下载预算。
- 健康检查优先让位于正在进行的补备，配额不足时推迟；补备失败的重试等待期间，仍继续检查健康主连接。已建立的业务继续持有原连接。

`64 MiB/分钟` 是配额补充速度，允许使用存下的突发额度；它不是每个自然分钟内绝对不超过 64 MiB。任意持续 t 秒的窗口，计费量上限为 `96 + 64 × t / 60 MiB`。默认每秒新建 4 条连接、每 80 条轮换，正常补备约 48 MiB/分钟，健康检查另需平均 3.2 MiB/分钟，可落在默认配额内。

新参数完整示例见 [clnt.cloudflare.toml](../examples/clnt.cloudflare.toml)，详细说明见 [Cloudflare 配置](cloudflare.md)。没有提高 112 次硬预算，也没有降低 100 Mbps 入选门槛。

## 原问题的相同负载复测

Release、本机回环、真实 OpenSSH `cat` 回显、模拟 SSE；每秒目标 4 条新模型 TCP 连接，另有固定 HTTP Keep-Alive 和 SSH 会话，持续双向各 200 Mbps。模型模拟首段计算约 25 ms，每个后续内容间隔约 20 ms。每个版本的预算压力诊断各运行一次 75 秒，表中最大值是这次观察，不是跨网络的延迟上界。

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 新连接模型请求完成数 | 242 | 300 |
| 新连接首段 p95（ms） | 27.505 | 27.494 |
| 新连接首段 p99（ms） | 27.834 | 27.879 |
| 新连接首段最大值（ms） | 14837.927 | 28.217 |
| 新连接首段 >100 ms | 1 | 0 |
| Keep-Alive 首段 p99（ms） | 27.408 | 27.557 |
| SSH p99（ms） | 1.494 | 1.432 |
| SSH 最大值（ms） | 1.689 | 1.768 |
| SSH >100 ms | 0 | 0 |
| 累计分配的业务 TCP | 255 | 313 |
| 单条外层连接最多分配数 | 112 | 80 |

优化前三次主连接选择，第二条主连接耗尽 112 次预算后等待约 15 秒；这次请求的停顿使串行调用方少发出了后续请求。优化后共选择四次主连接，三次正常补备均在前一次提升后立即启动，耗时 **18、18、20 ms**，提前准备好后续备用，累计分配 313 条业务 TCP，单条最高 80。

本轮新代码计费并成功下载的测速有效载荷为 **136 MiB = 88 MiB 启动 + 3 × 16 MiB 补备**；每次补备的计费量与完成日志相符。优化前记录完成了两轮完整候选筛选，按配置计算为 176 MiB，但旧版没有记录逐请求下载计费日志，因此不把它表述为精确的线速流量测量。新的 136 MiB 同样不包含 TLS、gRPC 头和轻量检查的开销。

首段 p99 优化前本来就只有约 28 ms，未反映那一次 14.84 秒停顿；这里同时报告最大值与 >100 ms 次数，避免漏掉稀有长尾。

## 稳态性能重新对比

使用优化后的同一组二进制，重新执行空闲、下载、上传、双向各 200 Mbps、不限速双向五种场景；两种模式各三轮，每轮预热后测 10 秒，交替运行顺序。每场景每模式合并 120 次新连接模型样本、120 次 Keep-Alive 模型样本和 600 次 SSH 样本，nearest-rank 计算分位数。单元中保持累计连接数低于 80，使该组指标衡量稳态传输；轮换行为由上方持续测试覆盖。

单位为 ms，吞吐为 Mbps。所有首段数值包含约 25 ms 模拟计算等待。

| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 无大流量 | 独立 TLS | 0.00 / 0.00 | 29.997 | 27.228 | 1.577 | 1.735 |
| 无大流量 | CF 复用 | 0.00 / 0.00 | 27.490 | 27.180 | 1.751 | 2.075 |
| 不限速下载 | 独立 TLS | 19831.96 / 0.00 | 28.303 | 26.566 | 1.355 | 1.459 |
| 不限速下载 | CF 复用 | 6974.08 / 0.00 | 28.453 | 27.074 | 1.476 | 2.862 |
| 不限速上传 | 独立 TLS | 0.00 / 18353.11 | 28.466 | 26.910 | 1.832 | 2.259 |
| 不限速上传 | CF 复用 | 0.00 / 7161.85 | 27.565 | 26.473 | 1.602 | 1.845 |

本轮稳态共 2,400 次模型请求、6,000 次 SSH 交互，全部成功；SSH 最大值为 4.857 ms，超过 100 ms 的样本为 0。不限速模式实际承载流量不同，不能单凭 SSH 尾延迟高低比较隔离能力；等负载比较应看双向各 200 Mbps 行。

## 验证与适用范围

格式检查、Clippy、13 项单元测试通过。端到端回归 23 项用例中 22 项通过，65 秒模型预填充测试按默认设置跳过；最终改动的失败补备、立即补备、硬预算三项另行复跑通过。新增覆盖包括：成功补备无固定冷却、失败时有限尝试后退避、没有备用时仍检查健康主连接、配额耗尽仍遵守硬预算，以及配额突发和补充速率。

测试仍为 Linux 本机回环，Intel Core Ultra 9 185H，两个代理各 4 个 Tokio 工作线程，真实 OpenSSH 会话、受控 SSE 后端。固定流量是应用端发送节奏控制，没有模拟 WAN 带宽排队或丢包，也没有连接真实 Cloudflare 边缘或运行真实模型推理。正式性能测试串行运行，没有并行编译或另一组压测。

此次消除了健康备用补充被固定成功冷却阻挡的问题。候选不合格、实际网络故障、测速配额太低或新连接速率超过配额支持能力时，硬预算仍会等待并可能超时；没有通过放弃测速、跳过证书验证或突破硬预算来隐藏这些情况。
