# 独立 TLS 与 CF 复用：模型流式首段和 SSH 交互

测试日期：2026-10-31。本报告保留补备优化前的 Release 测量结果；当前实现及优化后复测见 [补备优化报告](refill-performance.md)。此处原始数据不改写。

稳态测试中，固定双向各 200 Mbps 时，两种模式都没有出现明显的 SSH 交互停顿；CF 复用减少了新建模型连接的首段等待，HTTP Keep-Alive 请求的差距很小。默认连接轮换预算另做持续测试，结果见下文，不能仅凭稳态分位数判断持续短连接场景。

## 测试范围与方法

- Intel Core Ultra 9 185H，Linux 本机回环；clnt、srv 各 4 个 Tokio 工作线程。使用相同 Release 二进制，SHA-256 保存在原始 JSON。
- **CF 模式测试的是本地 gRPC 主备复用实现，没有连接真实 Cloudflare 边缘。** 两种模式均启用 TLS 和证书验证，保留默认 TLS 会话恢复行为。
- 临时 OpenSSH 10.6p1 服务、临时 Ed25519 密钥、严格主机密钥验证，独立端口，不改系统 SSH 配置。建立实际加密 SSH 会话，以 `cat` 回显模拟键入与回复；不分配 PTY，不包括终端绘制或实际维护命令耗时。
- 受控 SSE 服务模拟 OpenAI 风格模型 API：先返回 HTTP 头，等待约 25 ms，再发出首条内容；后续内容间隔约 20 ms，共 3 条，最后发出 `[DONE]`。不是 Strata/Ollama/vLLM 的真实推理测试。
- **首段延迟 TTFT**：调用开始到收到第一条完整 SSE 内容。新连接样本包含公网侧 TCP 建连和 RVNX 的业务隧道建立；Keep-Alive 样本使用已建立的同一 HTTP 连接。HTTP 头到达不算模型首段。
- 每个测量单元预热后记录 10 秒；新连接请求和 Keep-Alive 请求各 4 次/秒，同时每 50 ms 测一次 SSH 回显。每种负载分别执行 3 轮，交替模式顺序，总计 30 个单元。
- 下载/上传各开 4 条业务连接；双向同时开 8 条。固定流量场景每个方向合计 200 Mbps；不限速场景尽可能持续传输。上传在结束时核对接收端确认的总字节数。
- 主对比每单元重启代理，先完成候选筛选和预热，累计业务连接保持在 80 以下。CF 使用默认 6 候选、4/16 MiB 测速、100 Mbps 门槛及 80/112 预算。实测每单元都只选择过一次主连接；初始测速与 SSH 登录不计入延迟样本。
- 表中分位数将同一场景、同一模式的三轮**原始样本合并**后计算，使用 nearest-rank：每组新连接模型 120 次、Keep-Alive 模型 120 次、SSH 600 次。吞吐按测量时长加权平均。主对比共 2,400 次模型请求、6,000 次 SSH 交互，零错误。

负载发生器与模拟后端各自运行，模型和大流量后端共享一个 Python 事件循环。结果包含 Python、内核调度、后端和代理开销。JSON 另记负载发生器事件循环延迟与首条内容从后端发出到接收的时间，不能将总首段延迟全部归因于 TLS。

## 模型首段延迟

单位 ms；其中包含约 25 ms 的模拟模型首段计算等待。

| 负载 | 模式 | 新连接 p50 | 新连接 p95 | 新连接 p99 | Keep-Alive p95 | Keep-Alive p99 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 无大流量 | 独立 TLS | 28.453 | 29.707 | 30.059 | 27.159 | 27.576 |
| 无大流量 | CF 复用实现 | 26.791 | 27.575 | 27.757 | 27.198 | 27.377 |
| 不限速下载 | 独立 TLS | 27.499 | 28.463 | 28.731 | 26.743 | 27.825 |
| 不限速下载 | CF 复用实现 | 27.528 | 28.665 | 29.256 | 27.135 | 28.008 |
| 不限速上传 | 独立 TLS | 27.897 | 28.877 | 30.112 | 27.107 | 28.132 |
| 不限速上传 | CF 复用实现 | 26.846 | 27.552 | 28.251 | 26.436 | 26.845 |
| 双向各 200 Mbps | 独立 TLS | 28.046 | 29.622 | 29.838 | 27.427 | 27.778 |
| 双向各 200 Mbps | CF 复用实现 | 26.553 | 27.419 | 28.102 | 27.002 | 27.801 |
| 不限速双向 | 独立 TLS | 30.136 | 32.205 | 33.038 | 29.034 | 29.911 |
| 不限速双向 | CF 复用实现 | 28.222 | 29.404 | 30.433 | 27.151 | 27.447 |

无大流量时，新连接 p95 从 29.707 ms 降到 27.575 ms，差约 2.13 ms；Keep-Alive 的 p95 为 27.159 / 27.198 ms，基本相当。固定双向各 200 Mbps 时，新连接 p95 为 29.622 / 27.419 ms，Keep-Alive p95 为 27.427 / 27.002 ms。

固定 200 Mbps 场景中，新连接的 HTTP 头 p95 为独立 TLS 3.779 ms、CF 1.531 ms；首条内容从模拟后端发出到接收的 p95 分别为 0.527 / 0.462 ms。差别主要体现在新连接建立阶段，不能解读成每个模型 token 都能快 2 ms。

同一场景下，后续内容间隔 p95 为 21.411 / 21.445 ms，接近后端设定的 20 ms；没有观察到等待完整回答后再一起交付的现象。

## 大流量时的 SSH 交互

延迟单位 ms，下载/上传方向以映射端口访问者为准。吞吐只算业务有效载荷，不算 TLS、gRPC 和 SSH 协议字节。

| 负载 | 模式 | 下载 / 上传 Mbps | SSH p50 | SSH p95 | SSH p99 | 最大 | >100 ms |

| 无大流量 | 独立 TLS | 0.00 / 0.00 | 0.921 | 1.495 | 1.686 | 2.066 | 0/600 |
| 无大流量 | CF 复用实现 | 0.00 / 0.00 | 0.932 | 1.541 | 1.695 | 1.779 | 0/600 |
| 不限速下载 | 独立 TLS | 19577.10 / 0.00 | 0.591 | 1.199 | 1.379 | 2.359 | 0/600 |

| 不限速上传 | 独立 TLS | 0.00 / 17057.41 | 0.509 | 1.290 | 1.878 | 2.386 | 0/600 |
| 不限速上传 | CF 复用实现 | 0.00 / 7107.57 | 0.817 | 1.425 | 1.731 | 2.473 | 0/600 |
| 双向各 200 Mbps | 独立 TLS | 200.06 / 199.93 | 0.697 | 1.405 | 1.581 | 1.905 | 0/600 |
| 双向各 200 Mbps | CF 复用实现 | 200.03 / 199.99 | 0.567 | 1.209 | 1.438 | 2.453 | 0/600 |
| 不限速双向 | 独立 TLS | 12267.29 / 12157.71 | 1.480 | 3.399 | 4.310 | 5.248 | 0/600 |
| 不限速双向 | CF 复用实现 | 4112.54 / 4093.32 | 1.259 | 2.255 | 2.700 | 3.285 | 0/600 |

固定双向各 200 Mbps 时，SSH p99 为 1.581 / 1.438 ms；不限速双向时为 4.310 / 2.700 ms。主对比全部 SSH 样本的最大值为 5.248 ms，超过 50 ms、100 ms 的样本均为零。因此，**在本机这组负载中，大流量没有造成明显的 SSH 交互停顿**。

不限速双向下，独立 TLS 合计约 24.43 Gbps，CF 复用约 8.21 Gbps，实际承载流量相差约 3 倍。不能据此把 CF 更低的 SSH 尾延迟解释为更强的隔离；等流量比较应看 200 Mbps 场景。这里的吞吐是本机回环的观测值，不是公网或 CF 能力上限。

固定双向各 200 Mbps 下，两个代理进程合计平均使用约 0.204 / 0.246 个 CPU 核心；不限速双向为 6.447 / 3.383 核心。后者的流量并不相等，不能据此推算 CF 加密效率更高。不限速双向时，负载发生器事件循环延迟 p99 为 2.875 / 0.779 ms，同机调度竞争也参与尾延迟。

## 默认轮换预算持续测试

额外运行一次 75 秒 CF 测试，固定双向各 200 Mbps，持续以目标 4 次/秒新建模型 TCP 连接，同时保留一条模型 HTTP Keep-Alive 和一条 SSH 会话。生产默认预算、测速大小与 `retry_secs = 60` 均未修改；把测试工具的请求超时提高到 90 秒，允许记录代理等待的完整时长。

| 指标 | 结果 |
| --- | ---: |
| 新建连接模型请求 | 242 次，全部成功 |
| 新连接 TTFT p95 / p99 | 27.505 / 27.834 ms |
| 新连接 TTFT 最大值 | **14,837.927 ms** |
| 新连接 TTFT >100 ms | **1 / 242** |
| Keep-Alive 模型请求 | 300 次，全部成功 |
| Keep-Alive TTFT p95 / 最大值 | 26.914 / 27.589 ms |
| SSH 回显 | 1,500 次，全部成功 |
| SSH p99 / 最大值 | 1.494 / 1.689 ms |
| SSH >100 ms | 0 / 1,500 |
| 实际下载 / 上传 | 200.01 / 200.00 Mbps |
| 主连接选择次数 / TCP 累计分配 | 3 / 255 |

这次 **14.84 秒首段等待是默认补备节流与硬预算共同触发的等待**。相对于最初主连接选定时刻，日志显示：

- 约 +17.93 秒：达到软预算，切换到已测速备用。
- 约 +45.93 秒：第二条主连接累计分配到 112，新的业务连接需要等待备用。
- 约 +60.99 秒：完成下一轮筛选并提升新主连接，等待的模型请求恢复。

代码对成功筛选和失败重试均设置 60 秒间隔（`common/src/cloudflare.rs` 中 `retry_at`）；硬预算分支停止新 Attach 分配。该请求等待 HTTP 头约 14,812.694 ms，首条 SSE 内容总耗时 14,837.927 ms，后端内容发出到接收仅 0.247 ms。记录与代码路径一致；当时实际业务吞吐保持 200 Mbps，已有 SSH 与 Keep-Alive 请求继续正常。

仅看 p99 会漏掉这一次长尾。目标 4 次/秒指单个串行调用方的发起节奏，等待期间该调用方没有继续积压请求，所以新连接完成数低于 Keep-Alive 的 300 次。这是一次针对预算路径的诊断测试，没有把单次最大值当作稳定的公网等待上界。

低延迟优化应优先处理**备用补充时机与预算等待**，并让模型调用端使用 HTTP Keep-Alive。简单缩短 `retry_secs` 会增加每轮约 88 MiB 的测速流量；后续应同时权衡提前补备和测速开销。本轮只验证并记录问题，保留现有策略。

## 如何使用结果

对于长时间保持 HTTP 连接的模型调用，本轮看不出 CF 复用带来显著的首段收益；它主要节省新业务连接的握手等待。当前独立 TLS 默认值仍合理，CF 模式用于需要 CF 接入与优选主备的部署。

本地固定 200 Mbps 采用应用端发送节奏控制，**没有模拟 200 Mbps 网卡瓶颈、排队或丢包**。本轮也未覆盖真实 CF 的 RTT、回源路径、共享 TCP 的丢包重传等待、5 分钟带宽健康检查或真实模型推理负载。因此，结果支持本机稳态和预算行为的判断，不能承诺公网大流量时 SSH 同样只有几毫秒延迟。

## 复现与原始数据

需要 Linux、Python 3、OpenSSH 客户端/服务端、OpenSSL；以当前用户启动临时本地 SSH 服务。脚本结束会停止测试进程、删除临时密钥和配置，不留下常驻压测。

```sh
cargo build --release --workspace --locked
python3 tests/bench_streaming.py --seconds 10 --repeats 3 \
  --output docs/benchmarks/streaming-2026-10-31.json

# 单独观察生产默认的轮换预算，不与主测试同时运行
python3 tests/bench_streaming.py --modes cf --allow-rotation \
  --model-timeout 90 --seconds 75 --repeats 1 --scenarios duplex_200mbps \
  --output docs/benchmarks/streaming-policy-2026-10-31.json
```

[主对比原始样本](benchmarks/streaming-2026-10-31.json)保存全部模型首段、HTTP 头、后端交付延迟、内容间隔、SSH 往返、调度延迟及每轮吞吐、错误、CPU 时间和二进制哈希；[预算持续测试](benchmarks/streaming-policy-2026-10-31.json)另保留 CF 连接分配与切换日志。所有正式测量均串行运行，没有同时编译或执行另一组压测。本轮新增测试脚本和报告，没有修改代理实现或默认策略。
