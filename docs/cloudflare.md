# Cloudflare 优选 IP 与稳定主备

客户端配置中添加 `[cloudflare]` 即开启此模式；删除该节恢复默认的每条业务连接独立 TLS。CF 模式将本进程的映射放在同一个主备管理器下，不与 `multiplex = true` 或映射级 `multiplex` / `dedicated_pool_size` 混用。需要 SSH 保持独立传输时，可用另一份客户端配置、另一个进程注册 SSH 映射。

使用 [客户端样例](../examples/clnt.cloudflare.toml) 和 [服务端样例](../examples/srv.cloudflare.toml)。域名、候选 `IP:port` 和全部策略参数均可配置；样例中的 `192.0.2.x` 是文档占位地址，需要替换。不会扫描网段、下载公共 IP 列表或自动修改 DNS。启动时读取配置，修改后重启客户端。

## CF 接入

CF 模式采用标准 gRPC 双向流：HTTP/2、`application/grpc+proto`、protobuf 消息帧和 `grpc-status` trailers。协议声明在 [rvnx.proto](../proto/rvnx.proto)。原有直连模式继续使用 `/api/stream`；普通双向 POST 本身不足以保证经过 CDN 后仍有相同的流式行为。

```text
clnt → 指定候选 CF IP:443 → Cloudflare → srv:443
          TLS SNI 与 HTTP :authority 始终使用配置的域名
```

需要在 Cloudflare 中开启域名代理和 gRPC，源站在 443 提供 TLS、HTTP/2 与 h2 ALPN；建议使用 Full (strict)。Cloudflare 官方要求至少 Full，关闭 gRPC 时会返回 403。此方案用于普通代理域名，Cloudflare Tunnel 的公网 hostname 当前不支持 gRPC；也不能用 Cloudflare Access 替代 RVNX 令牌认证。[官方配置与限制](https://developers.cloudflare.com/network/grpc-connections/)。

客户端 `server` 写域名与端口，`server_name` 写同一域名。连接时只把 TCP 目标换成候选 IP，不改变 SNI、证书校验或 HTTP 请求域名。`tls_ca = ""` 或省略时使用内置公共根证书；本地测试可指定自己的 CA。CF 终止边缘 TLS，再以 TLS 回源，因此 CF 能看到隧道内的应用数据和 RVNX 认证头；SSH 仍有自身端到端加密。

`cf_probe_enabled = true` 在服务端启用同域名、同令牌的测速端点。未认证请求、未知路径和关闭的测速端点均返回普通 404。测速单次最多 16 MiB，全服务端最多并发 4 个测速/轻量检查请求；超限返回 gRPC 资源不足。测量使用 POST、禁止缓存、无压缩的随机数据；客户端检查实际收到的长度及结束状态。

模型 API 与 SSH 的公网入口仍是 srv 配置的映射端口。CF 代理的是 clnt 到 srv 的隧道；不会自动替模型 API 添加 HTTPS、API key，也不会自动把 srv:2222 变成 CF 可代理的 SSH 端口。模型入口配置参照 [Strata 文档](strata.md)。

## 策略

1. 同时建立 6 条候选 TLS 连接，先用轻量请求完成认证，再逐条下载 4 MiB。按速率取前两名，每条再下载两次 16 MiB，取较低值评分。测速逐条进行，避免候选相互争抢带宽。下载耗时包含请求往返，单位为十进制 Mbps；只有达到 100 Mbps 的连接才入选。
2. 最佳候选成为主连接，另一条合格候选成为备用。只有一个合格候选时先启用主连接，后台继续准备备用；没有合格候选时等待重试。健康主连接不会因为新备用评分更高而切换。备用一旦提升或失效，立即开始正常补备，不等待成功筛选后的冷却时间：优先在当前可用 IP 上建立新 TLS 连接，每次下载 8 MiB、复测两次取较低值，仍需达到 100 Mbps。首个合格候选即成为备用；不合格时才换候选，每轮最多尝试 2 条。单次速度已低于门槛时提前停止该候选的后续下载。
3. 主、备每 12 秒在自己的原有 HTTP/2 连接上发送一次零字节 Download 请求，校验到源站的完整路径。主连接每 5 分钟下载 16 MiB 检查；连续两次低于 50 Mbps 才判定低速异常，恢复到门槛即清零计数。连接故障直接触发故障处理。测速检查与筛选不同时进行，筛选期间或测速配额不足时会推迟带宽健康检查，轻量保活继续执行。补备失败的重试等待期间仍会检查健康主连接。
4. 主连接累计分配 80 条业务 TCP 隧道、出错、被要求轮换或没有并发容量时，优先提升已测速的备用；随后立即补充备用，使新主连接刚启用、预算尚充足时就开始准备下一条。只有整轮没有合格候选才按 `retry_secs` 等待重试。候选评分只属于那条实际 TLS 连接，重连后必须重新测速。会检测本地外层连接结束以及 HTTP/2 拒绝新流；无法直接观测 CF 内部边缘到源站连接的变化。
5. 若备用尚未准备好，健康主连接可继续接收业务，累计到 112 后停止分配新的 TCP 隧道，等待备用或排队超时。队列等待默认 60 秒，超时明确失败，不突破预算。服务端每个 TCP 映射应设置 `connection_wait_secs = 120`，覆盖等待及握手时间；直连默认仍为 10 秒。
6. 新连接切向新主连接，旧业务持有原连接直至完成，不主动关闭旧下载或 HTTP Keep-Alive。HTTP 同一 TCP 连接上的多个请求只计一次；注册控制流、UDP 会话、保活和测速不计入 TCP 累计预算。一次 Attach 分配即计数，后续失败也不退回，避免反复失败绕过预算。

80/112 是 RVNX 的可配置累计策略；代码中的 128 是每条连接的**并发 HTTP/2 流上限**，没有“累计 128 次自动轮换”的内置逻辑。实际分配还取对端声明的并发容量与 128 的较小值，并预留两条流用于检查。

正常稳定状态保留主、备两条连接；筛选期间会临时增加候选，轮换后还可能保留正在传输的旧连接。最初注册的控制流或 UDP 流可能长期留在旧连接上，直到对应映射结束才回收，因此“两条”不是整个进程的连接数硬上限。网络实际断开无法保留其上的传输；控制流断开仍会导致所属映射重连、释放其数据连接。计划轮换不触发这种清理。

## 配置与流量成本

所有参数的默认值见完整客户端样例。重点参数：

| 配置 | 默认 | 含义 |
| --- | --- | --- |
| `candidates` | 必填 | IP:port 列表，IPv6 使用 `[IPv6]:443`；轮次间循环取候选 |
| `candidate_count` | 6 | 启动完整筛选的候选数；列表较短时，同一 IP 建立多条独立候选连接 |
| `quick_download_mib` | 4 | 首轮每条连接下载量 |
| `final_download_mib` / `final_samples` | 16 / 2 | 启动前两名复测大小 / 次数；正常补备也使用此次数，取最低速度 |
| `refill_download_mib` | 8 | 正常补备的单次下载量；默认两次共 16 MiB |
| `refill_attempts` | 2 | 补备每轮最多尝试的连接数，成功即停止 |
| `probe_budget_mib_per_minute` | 64 | 全局测速配额每分钟补充量 |
| `probe_burst_mib` | 96 | 配额桶上限及启动时可用配额；必须覆盖最大的单次测速 |
| `target_mbps` / `slow_mbps` | 100 / 50 | 入选 / 低速门槛 |
| `keepalive_secs` | 12 | 主备轻量保活周期 |
| `health_interval_secs` / `health_download_mib` | 300 / 16 | 主连接带宽检查周期 / 大小 |
| `slow_failures` | 2 | 连续低速次数 |
| `rotate_after` / `hard_budget` | 80 / 112 | 软轮换 / 硬等待累计连接数 |
| `queue_timeout_secs` | 60 | 新隧道等待可用主连接的最大时间 |
| `probe_timeout_secs` | 30 | 每次完整测速的最大耗时 |
| `retry_secs` | 60 | 完整筛选或补备失败后的重试间隔；成功不触发等待 |

首次完整筛选仍为 `6 × 4 + 2 × 2 × 16 = 88 MiB`；正常补备首个候选合格时只下载 `2 × 8 = 16 MiB`，比原来每次重做完整筛选少约 82%。新连接必须实测，不继承原连接的速度。8 MiB 样本比启动时的 16 MiB 样本短；希望延长复测可提高 `refill_download_mib`，并相应提高流量配额。

本客户端进程的所有映射中，启动筛选、补备、健康下载共用一个配额桶：默认初始可用 96 MiB，以 64 MiB/分钟补充，上限 96 MiB。任意持续 t 秒的区间，计费下载量不超过 `96 + 64 × t / 60 MiB`。这是允许突发的长期流量控制，不是把每次测速限速到固定 Mbps；单次测速仍全速进行，避免测到自身限速值。请求下载前预扣完整大小，失败和取消不退款；轻量零字节检查不占下载配额，TLS/HTTP 头等协议开销不计入此数。

以每秒 4 条新 TCP 连接、80 次轮换估算，正常补备约 48 MiB/分钟；每 5 分钟 16 MiB 健康检查另需平均 3.2 MiB/分钟，合计低于默认 64 MiB 配额。主连接健康检查正常执行时每天约 4.5 GiB。业务 HTTP Keep-Alive 请求不重复计数，因此长连接业务的补备开销通常更少。

成功补备不受重试间隔阻挡，失败仍有次数上限和重试等待；全局配额防止快速轮换引发无上限下载。若所有候选失败、测速配额耗尽或新建连接速率超过可持续补备能力，112 次硬预算仍会等待，随后可能排队超时。调低配额也会延迟启动；不能同时承诺任意请求速率下零等待和固定低测速流量。

CF 主备模式主动复用 TLS，避免每条业务重新握手；共享同一 TCP 的流也共享丢包重传等待。HTTP/2 流量控制隔离应用慢读，无法消除 TCP 层队头阻塞。测速下载会占用带宽，不构成对模型首段延迟或 SSH 延迟的保障。

## 验证

本地端到端测试覆盖真实 TLS/gRPC、独立 Python HTTP/2 与 protobuf 解码、认证和测速开关、TCP 半关闭、UDP、主备轮换保留旧传输、硬预算等待、外层连接故障提升备用、限速两次低速触发轮换，以及 SSE、HTTP Keep-Alive 计数和维护流在轮换后的交互。还覆盖成功补备不等待失败重试间隔、失败时有限重试、配额受限时仍遵守硬预算。策略单元测试覆盖保守评分、连续低速清零、软硬预算、配额突发上限和补充速率。

```sh
cargo test --workspace
cargo build --workspace
python3 tests/e2e.py
```

这些测试使用本地证书与回环候选 IP；尚未使用真实 CF 域名验证网络路径、吞吐或流量识别效果。部署后日志中的 `CF candidate measured`、`CF primary selected`、`CF TCP connection allocated`、`CF health measurement` 可用来核对评分、切换与累计计数；`CF probe budget charged` 记录计费下载量，`CF standby refill complete` 记录补备耗时及流量。不会因配置校验而联网测速。

优化前的 [模型流式首段和 SSH 实测](streaming-performance.md) 曾记录补备冷却导致 14.84 秒首段等待。本次调度与测速流量改动及复测见 [补备优化报告](refill-performance.md)。
