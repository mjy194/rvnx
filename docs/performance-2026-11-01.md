# 最新版本性能复测：独立 TLS 与 CF 复用

测试日期：2026-11-01。使用补齐测试后的当前生产源码重新构建 Release；测试期间串行执行场景，没有同时运行编译或其他 RVNX 压测。生产源码、测试脚本和二进制 SHA-256 见 [汇总数据](benchmarks/performance-summary-2026-11-01.json)。

本机稳态测试的 **2400 次模型请求、6000 次真实 SSH 回显全部成功**。双向各 200 Mbps 时，独立 TLS / CF 复用的模型新连接首段 p95 为 **29.314 / 27.589 ms**，SSH p99 为 **1.596 / 1.520 ms**。单独的 75 秒 CF 轮换测试也全部成功，新连接首段最大值 **27.954 ms**。

## 方法与范围

- Intel Core Ultra 9 185H，Linux 本机回环，Rust 1.90.0 Release（thin LTO），两个代理各 4 个 Tokio 工作线程；临时证书启用名称及证书校验。
- **CF 模式测的是本地 gRPC 主备复用实现，没有连接真实 Cloudflare 边缘。** 候选列表为同一个回环地址，启动仍建立默认 6 条候选连接；保持生产默认的测速大小、配额、80/112 连接预算与失败退避。
- 模型后端为受控 SSE：先返回 HTTP 头，约 25 ms 后发出首条内容，之后每约 20 ms 发送内容，共 3 条。首段延迟从调用开始计到第一条完整 SSE 内容，包含约 25 ms 模拟计算；不是实际 Ollama/vLLM 推理耗时。
- SSH 使用临时 OpenSSH 服务和真实加密会话，每 50 ms 测量一次 `cat` 回显；严格验证主机密钥，不分配 PTY。该指标不包括终端绘制和维护命令耗时。
- 五种负载、两种模式，各三轮；每单元预热后测 10 秒，交替模式顺序。每组合并 120 次新连接模型请求、120 次 HTTP Keep-Alive 请求及 600 次 SSH 回显，采用 nearest-rank 分位数。吞吐按测量时长加权平均。
- 每个方向 4 条大流量连接；双向共 8 条。200 Mbps 由应用发送节奏控制；没有模拟真实带宽瓶颈、排队或丢包。不限速结果反映本机整个测试链路的吞吐，不是公网容量上限。
- 稳态测量每单元重启代理，保持累计业务连接少于 80；持续轮换另测 75 秒，以每秒 4 次新连接模型请求并行保持模型 Keep-Alive、SSH 和双向各 200 Mbps。

没有重现旧版本触及 112 次预算后约 15 秒的补备等待。这个结论适用于本次候选全部健康、可用带宽充足的测试；候选失败或测速配额不足时，生产逻辑仍允许排队。测速量仅计算下载有效载荷，不含 TLS/gRPC 头和保活。

## 首次运行中断与修正

首次运行完成 18 个稳态单元后，下一单元的客户端收到连接拒绝，首批失败日志比服务端就绪日志早不到 1 ms，触发默认 60 秒失败退避；测试工具的 60 秒启动等待随后超时。这发生在预热前，未生成该单元的性能样本。

仅调整测试工具的启动顺序：确认服务端已监听后再启动客户端。随后从头重新完成全部 30 个稳态单元和单独轮换测试。首次运行的 18 个单元未并入正式统计，保留 [中断运行数据](benchmarks/streaming-2026-11-01-startup-interrupted.json) 和 [故障日志摘录](benchmarks/startup-interruption-2026-11-01.txt)。生产默认退避策略没有修改；部署时若源站尚未就绪，CF 冷启动仍可能等待该退避周期。

## 结论与复现

当前本机测量支持：CF 复用减少新连接建立开销，独立 TLS 的不限速吞吐更高；双向各 200 Mbps 时两者都保持了低延迟 SSH 交互。测试没有覆盖公网 RTT、丢包重传、实际 CF 回源路径或真实推理，因此不能承诺公网具有同样的延迟。75 秒轮换测试也没有覆盖默认 5 分钟健康下载周期。

```sh
cargo build --release --workspace --locked
python3 tests/bench_streaming.py --seconds 10 --repeats 3 \
  --output /tmp/rvnx-streaming.json
python3 tests/bench_streaming.py --modes cf --allow-rotation \
  --model-timeout 90 --seconds 75 --repeats 1 --scenarios duplex_200mbps \
  --output /tmp/rvnx-rotation.json
```

本次为避免工作盘空间不足，实际使用 `/tmp/rvnx-perf-2026-11-01` 作为 Cargo 构建目录，并通过 `--bin-dir` 指向其中的 Release 二进制。负载仅在本地回环产生，测试结束后停止临时代理、SSH 服务和模拟后端。
